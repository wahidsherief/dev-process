dev-process: Engineering Guide

An AI-assisted development process delivered as a Claude Code plugin.

Describes plugin version 1.4.1 (repository commit 49842b1, tag v1.4.1). Written from the plugin's files, not from plans.

How to read the labels. Current exists in the plugin today. Planned discussed and designed, not built. Optional / Future possible later, no commitment. Anything without a label is explanation.

Naming. Earlier drafts called the project levels Light and Full and tagged rules [L]. Since v1.4 they are Safe and Risk, and rules are tagged [S]. This guide uses the current names and mentions the old ones where they appear in the glossary. Plugin commands are namespaced, for example /dev-process:analyze; a bare /init is a Claude Code built-in, not this plugin. The guide shortens them to init, analyze and so on.

1. Introduction

What is dev-process?

dev-process is a Claude Code plugin. A developer describes a task in plain words. The plugin makes Claude choose the right kind of work (a quick edit, a bug fix, a new feature, a hotfix), apply only the engineering standards that matter for the code being changed, run checks, collect proof, and finish with a short summary. A named human still approves the change.

It is a set of instructions (skills), a few commands, three hooks, one reviewer agent and templates. It adds no runtime to your application.

Why did we build it?

AI assistants write code quickly, but without guardrails the results vary. These are the problems the plugin targets:

  • Inconsistent output. The same request produces different structure, naming and quality from one session to the next.
  • Missed standards. Developers forget company rules (tokens, indexes, logging, accessibility). The AI forgets them too unless told every time.
  • Expensive context. Re-explaining the process and re-reading the project every session costs tokens.
  • Recreated solutions. A modal or table already exists in the project, and the AI builds another.
  • Legacy risk. Old systems are hard to understand, and AI edits without tests can break hidden behavior.
  • Scope creep. A small fix turns into a refactor because "the file could be better".
  • Unrestricted autonomy. AI that deploys, force-pushes or reads secrets on its own is a risk.
  • Accountability. Someone has to own the decision to merge.

Philosophy: AI proposes and assists; engineering standards, automated checks and human approval keep the change controlled.

2. The problem we are solving

Without a process

  1. Developer
  2. AI
  3. Code
  4. Hope it is correct

With dev-process

  1. Developer
  2. Task understanding
  3. Automatic lane
  4. Relevant standards
  5. Reusable patterns
  6. Implementation
  7. Verification
  8. Short summary
  9. Human approval

Each step is small and has a purpose: understanding avoids wrong guesses; the lane sets how much ceremony the work needs; standards and patterns keep output consistent; verification and the summary turn "it works" into evidence; approval keeps a person accountable.

All steps are Current. They are carried out by Claude following the plugin's instructions; only part of the checking is automated (see section 16).

3. What dev-process is, and is not

It is

  • An AI-assisted engineering process
  • A routing layer: task, lane, area, standards
  • A standards guidance system, with a few enforced rules
  • A reusable-pattern registry (docs/PATTERNS.md)
  • A project-analysis mechanism (analyze)
  • Lightweight memory and state (docs/PROCESS.md, memory notes, summary/resume)
  • A bridge between AI speed and engineering discipline

It is not

  • A replacement for developers
  • A replacement for CI/CD or code review
  • A framework or library in your app
  • Tied to Laravel, React, PHP or any one stack
  • A tool that refactors whole projects on its own
  • A guarantee that AI code is correct

5. Terminology guide

Plugin
Simple: an add-on for Claude Code. Technical: a folder with a manifest (.claude-plugin/plugin.json) bundling skills, commands, agents and hooks that Claude Code loads together.
Skill
Simple: a written playbook Claude reads when it is relevant. Technical: a SKILL.md with a short description; Claude loads the full text only when the task matches that description.
Command
Simple: something the developer types, like /dev-process:analyze. Technical: a markdown file in commands/ that hands a request to a skill.
Hook
Simple: an automatic check that runs at a fixed moment. Technical: a script Claude Code runs before a tool call, after an edit, or when a prompt is sent. Exit code 2 blocks the action.
Agent
Simple: a helper with a narrow job. Technical: a sub-session with its own instructions. Here: standards-reviewer, read-only. Agents do not call other agents.
Lane
Simple: the type of work being done. Technical: a predefined workflow path (full flow, quick change, bug fix, hotfix, data fix, refactor, upgrade, spike, release, migration) with its own steps and short check.
Task
Simple: what the developer asked for. Technical: the current unit of work, recorded in docs/PROCESS.md with its lane and status.
Project tier (called "Standard" in v1.4)
Simple: how strict the project's rules are by default. Technical: the Standard: field in docs/PROCESS.md, either Safe or Risk. Stored once.
Light
Simple: the old name for the basic rule set. Technical: now called Safe. Rules tagged [S] (formerly [L]).
Full
Simple: the old name for the complete rule set. Technical: now called Risk: every rule, that is [S] rules plus untagged ones. Not to be confused with the "full flow" lane for new features.
Standard
Simple: a rule for how we build (for example "no hard-coded colors"). Technical: a numbered, checkable rule inside a standards skill, with expected evidence.
Pattern
Simple: a proven way we already built something (a modal, a table). Technical: a row in docs/PATTERNS.md with metadata and a pointer to the real source file. No code is copied.
Candidate pattern
Simple: suggested, not yet trusted. Technical: status Candidate; never applied automatically.
Approved pattern
Simple: a pattern a human has said to reuse. Technical: status Approved (or Active); applied automatically when a task clearly matches.
Baseline
Simple: a snapshot of how the system performs now. Technical: docs/BASELINE.md: build time, test count, coverage, query times. Created in migration stage 1; used to compare later.
Project analysis
Simple: a quick report on how the project meets the standards. Technical: analyze: samples code, reports Present, Partial, Missing or N/A per standard.
Deep analysis
Simple: a thorough, more expensive report. Technical: analyze deep: maps the project once, then re-checks only what changed.
Resume state
Simple: a note that lets you continue after clearing the chat. Technical: .devprocess/summary.md, written by summary and read by resume.
Human approval
Simple: a person says yes. Technical: a named approver on the PR; also hotfix approval, migration gates and release sign-off.
Guardrail
Simple: a limit that keeps work safe. Technical: a hook, deny rule, CI job, stop point or scope rule that constrains what the AI can do.
Scope
Simple: what the task is about. Technical: the lines and components a task changes or adds. Standards apply to these, not to untouched code.
Evidence
Simple: proof the work is done. Technical: test output, query counts and plans, screenshots, scan results, log lines. No proof, no "done".
Verification
Simple: checking the work. Technical: running lint, tests and scans, plus the lane's short check and, for large or risky changes, the reviewer.
Regression test
Simple: a test that stops a bug coming back. Technical: in the bug-fix lane, a test written first that fails for the right reason, then passes after the fix.
CI
Simple: automatic checks on every pull request. Technical: a workflow (template provided) for PR size, lint, types, tests, secret scan, dependency scan, checklist and "a fix changes a test".
MCP
Simple: a way to connect Claude to outside tools. Technical: Model Context Protocol servers. dev-process does not ship any; init only advises keeping an allowlist and starting read-only.
Token / context
Simple: the amount of text the AI reads and writes, which costs money and time. Technical: input, output and cached tokens in a session. Less irrelevant text in context means lower cost and fewer mistakes.
Stack-agnostic
Simple: works with any language or framework. Technical: the lanes and standards describe behavior, not a framework; Claude inspects the actual stack and project tooling does stack-specific enforcement.

Not every task loads every skill. A label change loads one lane skill and perhaps ui-check. It does not load db-check, ai-check or the migration playbook. That is how the plugin controls both quality (relevant rules only) and tokens (no irrelevant text).

7. Project standards: Safe and Risk

Earlier called Light and Full tiers. Renamed in v1.4 to avoid confusion with the "full flow" lane.

Why two levels exist

An internal prototype and a payments system should not carry the same checklist. Safe applies the essential rules to any work. Risk adds the rules that matter when the cost of a mistake is high.

Safe (default)Risk
Rules appliedOnly rules tagged [S]Every rule: [S] plus untagged
Reviewer agentNot used, unless the task itself is riskyUsed when the diff is over about 80 lines or touches auth, permissions, migrations or money
Analysisanalyze judges [S] rules; Risk-only gaps are listed as "Risk-only" rows, not failuresJudges all rules
Typical useInternal tools, prototypes, small fixesCustomer-facing systems, user data, payments, AI features

Rule: Risk = Safe + extra requirements. A Risk task applies every Safe rule too.

What [S] means

In each standards skill, a rule starting with [S] belongs to the Safe set. A rule with no tag is Risk-only. Examples of untagged (Risk-only) rules: performance budgets, backups with a tested restore, the full AI cost dashboard and per-user budgets, restrained-color and animation guidelines.

How the standard is determined today

  • Current init writes Standard: Safe to docs/PROCESS.md and CLAUDE.md. The developer is not asked. They can say "set this project to Risk" at any time.
  • Planned Automatic detection of the right project standard. Not implemented.

Project standard vs task-level risk escalation

Project standardTask risk escalation
ScopePersistent, stored onceTemporary, for that task only
TriggerThe team decidesThe task touches payments or money, customer or personal data, authentication or permissions, or migrations
EffectSets the default rule setThe untagged rules apply to the changed code and the reviewer is allowed. The project standard does not change
StatusCurrentCurrent, judged by Claude from the task; no script detects it

After an escalated task, the summary says so and may suggest once: "set the project to Risk?" It never changes the project standard by itself.

AI calls follow a middle path: in a Safe project, code that calls an AI provider applies three [S] rules (no secrets or customer data in prompts, a monthly spend cap, a usage log). The rest of ai-check applies in Risk.

Why a quick change should not carry feature overhead. A brief, plan and review for a one-line label change cost more tokens and time than the change itself, and developers will learn to route around a process that is heavy on trivial work. The lanes put the ceremony where the risk is. If a quick change grows past its limits, Claude says so and moves up to the full flow.

10. Scope protection

Hard rule 8 in the entry skill:

Fix or build what was requested and apply the relevant standards to the affected area. Do not bring unrelated existing code up to standard. Mention nearby technical debt only when useful ("Noticed, not changed"). If the fix itself requires changing an area, the changed code follows the standard.

Good

Bug in a dropdown: fix the dropdown, add a regression test, apply the UI rules to the lines changed (tokens, accessibility of that control). The summary says: "Noticed, not changed: 14 hard-coded colors elsewhere in the form."

Bad

Bug in a dropdown: redesign the whole page, replace colors, restructure the form, because other elements are not compliant. The diff grows, review gets harder, and unrelated behavior can break.

This prevents AI-driven scope creep in four places: the rule itself, a "Scope" line in every standards skill, a reviewer check that flags unrequested refactors as scope creep (Major), and the summary's "Noticed, not changed" line, which gives the team a decision instead of a surprise. Current (guidance and reviewer; not enforced by code)

11. analyze and analyze deep

analyze (light, default)

  • Purpose: a quick view of how the project meets the standards for the areas that exist.
  • Looks at: docs/ARCHITECTURE.md if present, config and dependency files, and a small sample per area. Never maps the whole project.
  • Why it is cheap: sampling, reuse of an existing map, only the standards skills for detected areas, and a short table as output.
  • Respects the project standard: judges [S] rules in a Safe project, all rules in a Risk project. Risk-only gaps show as "Risk-only" rows.
  • Reports: one mark per standard: ✓ Present, ⚠ Partial, ✗ Missing, — N/A, plus a scope (Current task, Project gap or Unrelated) and one line of evidence. Ends with at most three lines of key findings.
  • Changes nothing: reads code only. It writes one report file and fixes nothing.

12. Reusable patterns

Standards = how we should build. Patterns = proven ways we already built something.

The registry is docs/PATTERNS.md, one table. Each row has: name (for example standard modal), category (modal, data table, form, api, query, job, email), status, when to use, canonical source (path and symbol of the real implementation), and constraints. Current

Lifecycle

  1. Candidate
  2. Approved
  3. Active
  4. Deprecated
StatusMeaningUsed automatically?
CandidateSuggested, not reviewedNo
ApprovedA human said to reuse itYes
ActiveIn regular useYes
DeprecatedDo not use; the registry says what replaces itNever recommended

Only a human moves a pattern to Approved (the technical lead, or the developer when they say so). Claude never promotes a pattern on its own.

Commands

  • patterns lists Approved and Active patterns. patterns modal filters by category or name. patterns all includes Candidate and Deprecated. If the file is missing or empty it says so. It does not search the codebase.

Why the registry holds pointers, not code

The canonical source file stays the single source of truth. A copy in the registry would drift from the code and cost tokens to read and maintain. Claude reads the one real file when it needs it.

Example

  1. Approved "standard modal" exists
  2. New developer needs a modal
  3. Claude finds the pattern by category and name
  4. Reads only the canonical source
  5. Reuses it, adapts only what is needed
  6. Verifies

The summary says which pattern was used. A new developer does not recreate a modal that already exists.

What exists and what does not

  • Current Lookup when a task clearly matches an Approved or Active pattern; "apply the standard modal pattern" by name; suggesting a candidate after finished work ("Pattern candidate: name at path. Add as Candidate?"), added only if the developer says yes.
  • Planned / not built Automatic discovery of candidate patterns by scanning the codebase. Today candidates come only from Claude's suggestion at the end of a task.

Token benefit: reading one known file is cheaper than searching the project and writing a new component. The saving has not been measured yet.

What has been measured

Measured on a small fixture app (tests/fixtures/mini-app) with claude -p, same task with and without the plugin, 2 runs per cell. Source: tests/TOKEN-COST.md and tests/token-runs-v1.4.1.jsonl. The numbers are noisy because totals swing with the number of turns.

  • Overhead per task ranged from about +3% to +37%; full-flow features about +35%; median across the five scenarios about +18%.
  • Instruction size in v1.4.1: the entry skill is about 1,100 words; the always-loaded skill descriptions total about 324 words (436 in v1.4).
  • Not measured: any saving from fewer reworks, pattern reuse or resume; the cost of init, analyze or a reviewer run.

The plugin costs more tokens per task than plain Claude in these tests. Its case rests on quality and on fewer wasted rounds, which the pilot has to show. The token-report command (section 19) is built to measure exactly that and will say INSUFFICIENT DATA until enough runs are recorded.

14. Legacy project strategy

  • Understand before changing. The first step on a legacy project is to map and baseline, not to edit.
  • Targeted analysis. analyze samples; analyze deep maps once and saves docs/ARCHITECTURE.md for reuse. Current
  • Baseline. Migration stage 1 records build time, tests, coverage, bundle size, query times and known bugs in docs/BASELINE.md, and lists hidden behavior (jobs, emails, integrations, manual processes). Current
  • Changed-code-only scope. Everyday tasks on a legacy project follow rule 8: improve what you touch, report the rest.
  • Migration lane. Seven stages: discover and baseline, guardrails, decision record, safety net, migrate in slices, verify and release, retrospective. Four human gates (baseline and guardrails; decision record and critical-flow coverage; every slice PR; release sign-off).
  • Safety net. Characterization tests lock current behavior before code changes. The plugin refuses to skip this "because the old app has no tests" and offers the smallest set that covers one critical flow.
  • Regression protection. Old tests stay green; data changes use backup, dry run on a copy and reconciled counts.
  • No forced rewrite. Preferred approach is piece by piece beside the old system behind feature flags. A full rewrite is listed as "avoid".

Why incremental. A legacy system carries behavior nobody has written down. Rewriting or bringing everything to standard in one run removes the evidence you need to know what broke. Small slices, each with tests and a human gate, keep every step reversible.

Wording note: legacy-migration stage 5 still refers to the old step names (start, plan, build, review, done). Since v1.3 there is no separate start command; each slice goes through the normal flow. This is a leftover to tidy.

16. Enforcement model

1. Guidance

Skills and instructions: the lanes, the standards, scope rules, the summary shape. Claude follows them but nothing in code forces it. Current

2. Automated enforcement

Hooks, deny rules, lint and tests, CI, secret scans. These run whether or not Claude cooperates. Current (a small set)

3. Human control

The developer's decisions, the named approver, hotfix approval, migration gates, release sign-off.

LayerWhat is actually enforced today
Hook: before a tool runsBlocks reading .env files, force-push, deleting branches (local and remote), and recursive deletes of wide paths
Hook: before a prompt is sentBlocks prompts that contain a secret (private keys, cloud and API keys, tokens, connection strings with passwords, credential assignments). Also gives a one-time offer to run init in a project that is not set up
Hook: after an editRuns the project's lint and test commands from .devprocess/config.json; a failure goes back to Claude to fix
Project settingsDeny rules for .env, secrets folders, force-push (template settings.json.tpl)
CI template (GitHub)PR size (400 lines), lint, types, tests, secret scan, dependency scan, PR checklist check, and "a bug-fix PR changes a test". Mark the jobs as required in branch protection
Not enforced by codeThe frontend, backend and AI standards, scope protection, lane choice, the logging check. They rely on guidance and review

Why subjective standards are not forced through hooks. Rules like "restrained color", "one clear primary action per screen" or "an index that fits the query" need judgment about context. A hook that guesses would block valid work and teach developers to disable hooks. Deterministic rules (secrets, force-push, tests, size) go in hooks and CI. Contextual rules go to AI judgment plus human review.

Planned Moving more rules into deterministic checks was discussed (a machine-readable rule registry, per-rule severity, CODEOWNERS for sensitive folders). None of it is built.

17. Human approval model

AI proposes. Humans remain accountable for approval.

RoleDecision
ApproverA named person approves every PR. Set during init (defaults to the developer who ran it)
Technical leadApproves the plan for new or large work, design pages, migration gates 1 to 3, data-fix scripts, and pattern promotion
ReviewerThe standards-reviewer agent comes first (read-only, one pass, only for large or risky Risk-standard changes); the human approver comes last
Release ownerSigns off releases, Gate 4 of a migration, and data-fix rollbacks
Hotfix approverOne named approver (technical lead or on-call) reviews now; CI and hooks still run

Claude always stops at: the plan (new or large work), PR approval, hotfix approval, migration gates, release sign-off, anything destructive or hard to undo, anything against production, and Red-class data. Claude never deploys, rolls back or touches production.

Why high-risk changes get stronger review. Payments, personal data, authentication and migrations have costly failure modes. Task risk escalation applies the full rule set and allows the reviewer agent for those tasks, even in a Safe project.

token-report in detail

Data lives in .devprocess/token-runs.jsonl. Nothing is recorded automatically. Record runs with scripts/token-record.py (from claude -p --output-format json output, or typed numbers) using the same --task id for the same task with and without the plugin; add rework and review rounds later with --annotate.

  • It separates token overhead (extra tokens) from token efficiency (fewer rework and review rounds).
  • It needs at least 5 comparable tasks. Below that it prints "N/A — insufficient comparable data".
  • Verdicts: WORTH IT (at least 20% fewer rework or review rounds, neither worse than 10%), NOT YET WORTH IT, INSUFFICIENT DATA (including when there is no rework data). Lower token use alone never counts as efficiency.

21. Stack-agnostic design

The plugin contains no framework code. It works the same for PHP/Laravel, Node, React, Vue, Python, Java and others, because of how it is built:

  • Lanes are technology independent. A bug fix is reproduce, failing test, root cause, minimal fix in any language.
  • Standards are conceptual. "No N+1, index the filter columns, show the query plan" applies whatever the ORM. The skills say to run EXPLAIN, not a specific ORM call.
  • Skills inspect the actual stack. init detects language, framework and commands from the repo and records them in CLAUDE.md and .devprocess/config.json.
  • Stack-specific enforcement lives in project tooling. The CI template has placeholders for your lint, type, test and dependency-scan commands (for example npm audit, pip-audit, composer audit).
  • Orchestration, not replacement. The plugin steers behavior. Your framework, linters and test runners still do their jobs.

The evidence for this is limited: the evals and token tests run on one small Python fixture app. Behavior on other stacks has not been tested by us. Treat stack-agnostic as a design property, not a tested result.

22. How this was orchestrated

The principles used while designing the plugin:

  • Start from engineering problems (inconsistent output, scope creep, cost), not features.
  • Separate process from technology.
  • Use small specialized skills rather than one large prompt.
  • Route only the relevant context.
  • Minimize token use, and measure it instead of assuming.
  • Use hooks and CI for deterministic rules; use AI judgment for contextual ones.
  • Keep humans accountable for approval.
  • Reuse approved patterns.
  • Improve legacy systems incrementally.
  • Test the instructions themselves with evals (47 across 9 skills, LLM-graded and noisy; latest full run 126 of 158 assertions).

24. Current limitations

  • AI can still make mistakes. Evals on the plugin's own instructions score about 80% of assertions (126 of 158), vary between runs, and one backend scenario (db-check #1) is a known weak spot.
  • Standards are guidance, not magic. Most are not enforced by code. A developer or Claude can skip them; the reviewer and the approver are the backstop.
  • Existing technical debt is not eliminated. Scope protection means untouched code stays as it is.
  • Subjective quality needs human judgment. Visual restraint, naming and architecture choices are not machine-checked.
  • Stack-specific CI is the project's job. The template has placeholders only.
  • Deep analysis costs more tokens, and its incremental mode has not been run on a real project.
  • Pattern quality depends on human approval. A poorly kept registry gives poor reuse. Automatic pattern discovery is not built.
  • Cost is higher per task. Measured overhead is about +3% to +37% on a small test app. Savings from less rework are unproven.
  • The project standard is not auto-detected. It defaults to Safe; task risk escalation is judged by Claude.
  • Single-stack testing. Only a small Python fixture has been used.
  • Not yet used on a real project. The system improves a project progressively, not instantly.

25. Recommended adoption

Do not overwhelm developers. Most work is just typing the task. Introduce the commands one at a time.

StepCommandWhen
StartinitOnce per project. Takes the defaults, then continues the task
Understand current workanalyzeWhen you want a quick view of standards gaps
Need complete project understandinganalyze deepBefore legacy work or a migration; expect higher cost on the first run
Find reusable implementationpatternsBefore building a common component. Needs a maintained docs/PATTERNS.md
Save task statesummaryBefore clearing context or ending the day
Continue after clearing contextresumeStart of the next session
Judge the pilottoken-reportAfter recording at least 5 comparable tasks with and without the plugin

Suggested pilot

  1. Pick one project and one or two developers. Run init and review the generated files.
  2. Define pass and fail lines first: for example at least 20% fewer rework or review rounds and no increase in post-merge defects.
  3. Do at least 5 comparable tasks with and without the plugin; record tokens, rework and review rounds.
  4. Review a few PRs by hand to check that proof is real, not just claimed.
  5. Run token-report, decide, and extend the pilot if the result is unclear.
